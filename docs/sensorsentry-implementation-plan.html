Ground rules

Four rules that shape every decision below

Rule 01

Separate processes, always

The simulator and the detector are different programs talking over a socket. This is not tidiness — it is the proof the demo is not hardcoded, and it must be true from the first commit.

Rule 02

The detector never sees truth

No true position, no attack flag, ever crosses the socket. If a debugging shortcut needs it, the shortcut is wrong. Enforce this in code review.

Rule 03

Demoable beats complete

Get the two-path map on screen at Phase 3, before any clever detection exists. From then on every phase improves a working demo instead of risking one.

Rule 04

Zero false alarms is a gate

The clean-run scenario must finish with no alerts after every single phase. If that number ever leaves zero, stop and fix it before adding anything new.

Architecture

Three processes and a browser

Program A · test tool

Simulator

Vehicle motion model, sensor models, attack and fault injectors, scenario runner. Knows the truth and never shares it.

publishes UDP :5005
Program B · the product

Detector

The ten workflow stages. One instance per vehicle. Consumes sensor frames, emits verdicts, trust scores and incidents.

listens :5005 · serves WS :8080
Program C · fleet layer

Fleet service

Collects incidents from all detectors, clusters them in time and space, computes the attack zone, issues advisories.

listens :8090 · serves WS :8081
Browser

Console & phone app

One responsive web page. Wide screen becomes the operator console; phone screen becomes the fleet app. Same code.

connects WS :8080 / :8081

The console must not use online map tiles. You will be running with wifi off to prove the system is self-contained, and tiles would fail silently and leave a blank map. Draw the map yourself on a canvas — a grid, the route, the two paths, the attack zone. It also looks more like an instrument and less like a website.

Layout

Repository structure

sensorsentry/
simulator/
  vehicle.py          # motion model: drone and truck profiles
  sensors.py          # gnss, imu, baro, mag, odom — noise + drift
  attacks.py          # walk-off, teleport, alt-only, replay, magnet
  faults.py           # stuck, noisy, dropout, bias
  scenarios.py        # the six named scenarios
  publisher.py        # builds the frame, sends UDP
  control.py          # start / inject / reset HTTP endpoint

  ingest.py           # stage 1 — receive, time-align, buffer
  health.py           # stage 2 — per-sensor sanity
  deadreckon.py       # stage 3 — the GPS-free witness
  crossvalidate.py    # stage 4 — every pair scored
  blame.py            # stage 5 — who disagrees with everyone  ★
  classify.py         # stage 6 — attack / fault / interference ★
  trust.py            # stage 7 — scores with hysteresis
  fusion.py           # stage 8 — re-weight, fall back
  evidence.py         # stage 9 — append-only incident record
  server.py           # stage 10 — WebSocket out
  profiles.py         # which sensors and pairs per vehicle type

fleet/
  collector.py        # receives incidents from detectors
  cluster.py          # group by time + space          ★
  zone.py             # estimate attack area           ★
  advisory.py         # warn vehicles heading in       ★

console/
  index.html          # one responsive page: console + phone
  map.js  panels.js  ws.js  style.css

harness/
  sweep.py            # runs the strength ladder, writes the table
  regress.py          # clean runs — asserts zero false alarms
  results.py          # builds the results card

★ = the parts that make this project different. Protect them.
The build

Twelve phases

Effort figures assume a small team working in parallel where the phase allows it. The two outlined phases are gates — do not pass them until their condition is met.

PHASE 0

Foundations

~2 h
Build
  • Repo, folders, Python env with NumPy only.
  • Freeze the sensor-frame and verdict-frame schemas above.
  • UDP publisher and receiver sending dummy frames.
  • Decide local-metres coordinate frame; lat/lon only for display.
Done whenTwo separate processes are running and one is receiving frames from the other. Nothing else.
Enables everything
PHASE 1

Simulator — clean flight

~6 h
Build
  • Vehicle motion along a scripted route with turns, climbs, braking.
  • Sensor models with honest noise: GNSS jitter, IMU bias random-walk, baro noise, mag noise, wheel slip.
  • Publish frames at 20 Hz, GNSS updating at 5 Hz.
  • Seed the RNG per run and record the seed in the frame stream header.
Done whenA clean flight runs for three minutes and the frames look plausible when printed. IMU drift is realistic — this is what sets your detection limit later, so do not make it too good.
US-20
PHASE 2

Detector — witness and residual

~8 h
Build
  • ingest.py — buffer and time-align incoming frames.
  • health.py — stuck, out-of-range, dropout, excess-noise checks.
  • deadreckon.py — integrate IMU into an independent position with a growing uncertainty.
  • Compute the GNSS-versus-dead-reckoning residual and print it.
Done whenOn a clean run the residual stays small and bounded. Code review confirms GNSS is not read anywhere in the dead-reckoning path.
US-01, US-02
PHASE 3

Console v1 — the two-path map

Gate~6 h
Build
  • WebSocket server in the detector; browser client.
  • Canvas map: grid, route, GNSS-claimed path, dead-reckoned path.
  • Raw-feed panel showing incoming frames — the anti-hardcoding proof.
  • Start and Reset controls wired to the simulator's control endpoint.
Gate — do not pass untilYou can show this to somebody and they understand it without explanation. From here the project is demonstrable; everything after improves a working demo rather than gambling on one.
US-11, US-21
PHASE 4

Attacks and full cross-validation

~8 h
Build
  • Attack injectors: walk-off with adjustable speed and direction, teleport, altitude-only, replay.
  • Fault injectors: stuck value, excess noise, dropout, slow bias.
  • crossvalidate.py — score every applicable sensor pair, not just GNSS against one reference.
  • Strength slider and direction control in the console.
Done whenLaunching a walk-off attack visibly separates the two paths on the map, and every pair's score is visible in the console.
US-03, US-21
PHASE 5

Blame assignment ★

Unique~6 h
Build
  • blame.py — for each sensor, count disagreements; confirm the remainder still agree among themselves.
  • Name the guilty sensor and attach the failing pairs as evidence.
  • Return cannot_isolate when two or more sensors conflict — never guess.
Done whenSpoofing GNSS names GNSS. Injecting a magnet fault names the magnetometer. Injecting both at once returns cannot_isolate rather than a wrong answer.
US-04
PHASE 6

Attack-or-fault classification ★

Unique~6 h
Build
  • classify.py — measure directional consistency of the error over a window.
  • Steady and one-directional → attack. Erratic, or paired with a health failure → fault.
  • One measurement shifting while motion sensors report nothing → interference.
  • Below the confidence threshold → unclassified, defaulting to the safe response.
Done whenThe spoofing scenario reports attack, the broken-sensor scenario reports fault, and the magnet scenario reports interference — with no scenario-specific code anywhere in the classifier.
US-05
PHASE 7

Trust, hysteresis and fallback

~6 h
Build
  • trust.py — 0-to-1 score per sensor, moving smoothly, requiring N sustained cycles to downgrade and M to recover.
  • fusion.py — drop the untrusted sensor, keep navigating, publish a growing error budget.
  • Verdict panel and trust bars in the console.
Done whenThe hard-manoeuvre clean run finishes with zero alerts, and the spoofing run keeps the vehicle on its true route after detection.
US-06, US-07, US-08, US-10
PHASE 8

Truck profile

~4 h
Build
  • profiles.py — sensor set and applicable pairs per vehicle type.
  • Truck motion model, wheel odometry, and a simple road-network check.
  • The cargo-theft scenario: fake path stays on the road, real path stops behind.
Done whenSwitching to the truck profile requires no code change in the detector — only configuration. This is the claim you make on stage, so it must be literally true.
US-23
PHASE 9

Fleet service and attack zone ★

Unique~6 h
Build
  • Run four detector instances against four simulated vehicles.
  • cluster.py — group incidents inside one radius and time window.
  • zone.py — estimate centre and radius; draw it on the fleet map.
  • advisory.py — warn vehicles whose route crosses the zone.
Done whenFour vehicles attacked together produce one event and one circle. One vehicle alone produces no circle.
US-14, US-15, US-16
PHASE 10

Evidence, phone view, report

~6 h
Build

  • Replay mode: feed a stored record back through the detector.
  • Responsive layout so the same page works as the phone app; push the alert to it.
  • Optional written report, behind a visible on/off switch.

US-17, US-18, US-19, US-12, US-13
PHASE 11

Measurement harness

~5 h
Build
  • sweep.py — run attack strengths from 5 m/s down to 0.1, ten runs each, record detection time.
  • regress.py — twenty clean runs, assert zero alerts.
  • results.py — produce the results card and the strength ladder.
Done whenThe failure-boundary table in the demo playbook is filled with your measured numbers, not the placeholders. This harness produces both your results card and your credibility.

Hardening and rehearsal

~5 h
Build

Done whenSomeone outside the team can run the whole demo from the playbook without asking you a question.

Decisions

Choices to make once, now

Each of these is cheap to decide today and expensive to change in Phase 9.

DecisionChooseWhy
Coordinate framelocal metres (ENU)All maths in metres; convert to lat/lon only for display. Avoids a whole class of bugs.
Frame rate20 Hz frames, GNSS at 5 HzRealistic — GNSS genuinely updates slower than the IMU, and the gap matters to detection.
TransportUDP for sensorsMirrors real telemetry, and dropped frames become a case you must handle — which is realistic.
Randomnessnew seed each run, storedDifferent detection time every run (your proof), but exact reproducibility on replay.
Map renderingown canvas, no tilesWorks with wifi off. Looks like an instrument rather than a website.
DependenciesNumPy, nothing moreNo install surprises on demo day, and "we wrote the maths" survives scrutiny.
Filterstart simple, upgrade laterPlain residual comparison first. Add the Kalman innovation test in Phase 11 if time allows — it is credibility, not capability.
Splitting the work

Who builds what

The frozen data contract from Phase 0 is what lets these run in parallel. Nobody waits on anybody after that.

PersonOwnsPhases
A — SimulatorVehicle model, sensor models, attacks, faults, scenarios, control endpoint1, 4, 8
B — Detector coreIngest, health, dead reckoning, cross-validation, fusion2, 4, 7
C — The unique partsBlame assignment, classification, trust, fleet clustering and zone5, 6, 9
D — ConsoleMap, panels, controls, phone layout, evidence view3, 10

With three people: C's work goes to B, and A picks up the harness. With two: one takes simulator plus console, the other takes the whole detector — and cut Phase 9 to two vehicles instead of four.

Whoever owns Phase 5 and 6 should be your strongest person. Those two phases are the entire difference between this project and a threshold alarm.

Risks

What actually goes wrong, and the counter

RiskSign it is happeningCounter
Simulator perfectionismDay two and you are still tuning aerodynamicsThe simulator only has to be plausible. Time-box Phase 1 and move on.
Threshold tuning until it worksNumbers changed to make the attack tripRun regress.py after every change. Zero false alarms is a gate, not a goal.
Pretty console, empty enginePhase 3 grows into two daysPhase 3 ships ugly. Polish only in Phase 12.
Truth leaking into the detectorA debugging field quietly added to the frameAssert on the schema at ingest. Reject unknown fields loudly.
Fleet phase runs out of timePhase 9 not started with a day leftCut to two vehicles. The circle is what matters, not the count.
Never rehearsedFirst full run-through is in the roomPhase 12 is not optional. Book the time before you need it.

The single most likely failure of this project is spending the time on the simulator instead of the detector. The simulator is visible, satisfying and endless. The detector is where every mark is. If you are behind, cut simulator realism first — never cut Phase 5, 6 or 12.

Definition of done

The project is finished when all of this is true

  • Two processes run separately, and no truth crosses the socket.
  • Six scenarios are selectable and start within two seconds.
  • A clean run with hard manoeuvres produces zero alerts.
  • Spoofing is caught, GNSS is named, and the vehicle stays on its true route.
  • A broken sensor is reported as a fault, not an attack.
  • The magnet scenario is reported as interference.
  • The truck profile runs with configuration changes only.
  • Four attacked vehicles produce one event and one attack zone.
  • An incident replays to an identical verdict.
  • The strength ladder is filled with measured numbers, including the point where you fail.
  • The report switch turns off with no effect on detection.
  • The whole demo has been run end to end, out loud, five times.
