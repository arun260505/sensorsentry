Actors

Who uses the system

Two of these are people in the field, one is the software itself, and the rest appear only after an incident.

A1

Onboard detector

The software running on the vehicle. Not a person — it acts on its own every cycle, and most core stories belong to it.

A2

Fleet operator

Sits in the control room watching many vehicles. Receives alerts, decides responses. Our primary human user.

A3

Driver / pilot

In the cab or at the controls of one vehicle. Needs short, clear instructions, not data.

A4

Fleet manager

Owns the vehicles and the budget. Cares about incident history, losses avoided, and evidence.

A5

Insurer / investigator

Appears only after an incident. Needs a record they can independently verify.

A6

Integrator

Installs the software and registers vehicles with their sensor sets. One-time setup role.

In detail

The three that matter most

These are the ones judges will probe, so they are written out step by step — including what happens when things are not clear-cut.

UC-05 · Identify which sensor is lying

Actor: onboard detectorTrigger: any pair disagrees beyond its normal band
  1. Collect the agreement score for every checkable pair this cycle.
  2. For each sensor, count how many others it disagrees with.
  3. Check whether the remaining sensors still agree among themselves.
  4. If exactly one sensor disagrees with all the rest while they agree with each other, name it as the guilty sensor.
  5. Attach the supporting evidence: which pairs failed, by how much, for how long.

Result: a named sensor with evidence, not a generic alarm.

If it is not clear-cut: when two or more sensors disagree with the group, the system reports "cannot isolate — multiple sensors in conflict" and lowers trust on all of them. It must never guess. Guessing wrong is worse than admitting uncertainty, and judges will ask about this exact case.

UC-06 · Classify attack, fault or interference

Actor: onboard detectorTrigger: a guilty sensor has been named
  1. Look at the shape of the error over the last window, not just its size.
  2. Is it steady and pointing consistently one way? That is purposeful — an attack.
  3. Is it erratic, jumpy, or did the sensor also fail its own health check? That is a fault.
  4. Does one physical measurement shift while the motion sensors say nothing moved? That is interference in the environment.
  5. Publish the label with a confidence value and the reason behind it.

Result: the operator learns what kind of problem this is, not just that there is one.

If it is not clear-cut: below the confidence threshold, report "unclassified anomaly" and default to the safest response — treat it as an attack for safety purposes, but say plainly that the cause is undetermined.

UC-16 · Draw the estimated attack zone

Actor: fleet operatorTrigger: two or more vehicles report attacks close together in time and place
  1. Group incidents that fall within the same time window and the same area.
  2. Take the real positions of the affected vehicles at the moment each was hit.
  3. Estimate a centre and a radius covering those positions.
  4. Draw the zone on the fleet map and label it with how many vehicles are affected.
  5. Keep updating the estimate as more vehicles report or recover.

Result: a place on a map to send someone — the attacker's rough location.

If it is not clear-cut: with only one affected vehicle, no zone is drawn. One vehicle could be a fault, and a wrongly drawn zone would send people to the wrong place.

User stories

Written as the person who needs it

Seven epics. Stories with a blue edge are the ones that make this project different from a threshold alarm — protect them when time runs short.

EPIC 1

Sensor Trust Engine

Work out who is telling the truth
US-01P0UC-02

As the onboard detector, I want to check each sensor's own health every cycle, so that obviously broken sensors are caught before they corrupt any comparison.

Accepted when
  • A value frozen for more than N cycles is flagged as stuck.
  • Readings outside physical limits are flagged as out-of-range.
  • A sensor that stops sending is flagged as dropped within one cycle.
  • Noise beyond the sensor's rated band is flagged as degraded.
  • Every flag carries a reason code, never a bare boolean.
US-02P0UC-03

As the onboard detector, I want a position estimate built without ever reading GPS, so that I have a witness the attacker cannot reach.

Accepted when
  • An estimate is produced every cycle from motion, compass, pressure and wheels.
  • The estimate carries an uncertainty value that grows over time.
  • Code review confirms GPS is never an input to this path.
US-03P0UC-04

As the onboard detector, I want an agreement score for every checkable sensor pair, so that disagreement can be located and not merely noticed.

Accepted when
  • At least five pairs are scored every cycle for a drone; the truck profile scores its own set.
  • Each pair yields both a raw difference and a normalised score.
  • The full set of scores is available to the console, not hidden inside the engine.
US-04P0UniqueUC-05

As a fleet operator, I want to be told which sensor is wrong, so that I get a diagnosis instead of an alarm with no subject.

Accepted when
  • A sensor disagreeing with all others, while those others agree among themselves, is named as guilty.
  • The verdict lists the failing pairs and their magnitudes as evidence.
  • With two or more sensors in conflict the system reports cannot isolate and never guesses.
US-05P0UniqueUC-06

As a fleet operator, I want to know whether this is an attack, a breakdown, or interference, so that I take the right action instead of the safe-looking one.

Accepted when
  • Output is one of attack, fault, interference, or unclassified, with a confidence value.
  • A steady one-directional error over the window classifies as attack.
  • An erratic error, or one alongside a failed health check, classifies as fault.
  • A single measurement shifting while the motion sensors report no movement classifies as interference.
  • Below the confidence threshold the label is unclassified and the response defaults to the safest option.
US-06P0UC-07

As a fleet operator, I want trust to fall gradually and only on sustained evidence, so that a sharp turn never triggers a false alarm.

Accepted when
  • Each sensor carries a trust value from 0 to 100, moving smoothly.
  • A downgrade needs N consecutive cycles of disagreement; recovery needs M.
  • No single reading can change the trust state on its own.
  • The hard-manoeuvre scenario completes with zero alerts.
EPIC 2

Keep Running Safely

Detection is worthless without a response
US-07P0UC-08

As the onboard detector, I want to drop the untrusted sensor and navigate on the rest, so that the vehicle stays on its true route while under attack.

Accepted when
  • Fusion re-weights within one cycle of the trust drop.
  • Navigation continues without interruption, using the remaining sensors.
  • In the spoofing scenario the vehicle holds the real route while the reported position walks away.
US-08P1UC-09

As a driver, I want to see how fast our accuracy is decaying, so that I know how long we can keep going before we must stop.

Accepted when
  • An error budget in metres is published every cycle and grows visibly over time.
  • The display shows the remaining time until the budget exceeds a configured safe limit.
US-09P1UC-10

As a drone pilot, I want the vehicle to take a safe action by itself when trust collapses, so that it does not keep flying into danger while waiting for me.

Accepted when
  • The action is configurable per vehicle: hold, return, land, or reroute.
  • The action taken is written to the incident record.
  • The operator can override it at any time.
EPIC 3

Tell the Human

A detection nobody sees protects nobody
US-10P0UC-11

As a fleet operator, I want an alert within seconds naming the vehicle, the sensor and the cause, so that I can act while it still matters.

Accepted when
  • The alert reaches the console and the phone within 3 seconds of the verdict.
  • It contains vehicle id, guilty sensor, cause label, and the distance between claimed and real position.
  • It is written in plain words, with no jargon and no raw numbers as the headline.
US-11P0UC-12

As a fleet operator, I want both paths drawn on one map, so that I can see at a glance how far the deception has gone.

Accepted when
  • Claimed path and real path are drawn in distinct colours with a visible legend.
  • The separation distance is shown in metres and updates live.
  • Both paths remain visible after the incident ends, for review.
US-12P1UC-13

As a driver, I want to be told what to do, so that I am not interpreting numbers during the worst minute of my day.

Accepted when
  • Each cause label maps to one clear instruction.
  • Attack and fault produce visibly different instructions.
  • The instruction is one sentence a non-technical person can follow.
US-13P1UC-14

As a fleet operator, I want to acknowledge an alert, so that the rest of the team knows it is being handled.

Accepted when
  • Acknowledgement records who and when.
  • The alert changes state and stops repeating.
  • Dismissing an alert requires a reason, and the reason is stored.
EPIC 4

Fleet Attack Intelligence

One vehicle can be fooled — a fleet cannot
US-14P0UniqueUC-15

As a fleet operator, I want several vehicles hit at once in one area shown as a single attack event, so that I know it is a deliberate attack and not a run of coincidental faults.

Accepted when
  • Two or more incidents inside the same radius and time window group into one event.
  • The event lists its member vehicles and when each was hit.
  • Grouping raises the confidence of the attack classification for every member.
US-15P0UniqueUC-16

As a fleet operator, I want the likely attack area drawn on the map, so that I can tell the authorities where to look.

Accepted when
  • A centre and radius are estimated from the real positions of affected vehicles.
  • The zone is drawn on the fleet map with the number of vehicles affected.
  • The estimate tightens as more vehicles report.
  • No zone is drawn when only one vehicle is affected.
US-16P1UniqueUC-17

As a driver, I want a warning before I drive into a known attack area, so that I can avoid it rather than survive it.

Accepted when
  • Any vehicle whose route crosses an active zone receives an advisory.
  • The advisory suggests holding or rerouting.
  • The advisory clears automatically when the zone goes inactive.
EPIC 5

Evidence

In both our stories, the missing piece was proof
US-17P0UC-18

As a fleet manager, I want every incident recorded in full, so that I can prove what happened to my vehicle.

Accepted when
  • The record holds the timeline, the sensor readings around the event, the checks that fired, the verdict, both paths, and the actions taken.
  • Records are append-only — nothing can be edited after the fact.
  • A record can be exported as a single file.
US-18P1UC-19

As an investigator, I want to replay an incident, so that I can verify the conclusion myself instead of trusting it.

Accepted when
  • Replay feeds the stored raw readings back through the engine.
  • The replayed verdict is identical to the original, every time.
US-19P2UC-20

As a fleet manager, I want the incident written up in plain language, so that I can send it to the insurer without rewriting it.

Accepted when
  • The report is generated only from the stored structured record.
  • A visible switch disables it, and detection is completely unaffected when it is off.
  • It never invents a fact that is not in the record.
EPIC 6

Demo Control

The judges drive, not us
US-20P0UC-21

As a presenter, I want a list of scenarios the judges can choose from, so that the demo is theirs to direct and clearly not a recording.

Accepted when
  • At least six scenarios are selectable, covering drone and truck, attack and fault and interference, plus one clean run.
  • A scenario starts within two seconds of selection.
  • The same engine serves every scenario — nothing is special-cased per scenario.
US-21P0UC-21

As a presenter, I want to launch an attack at the moment I choose and reset instantly, so that I can respond to whatever the judges ask for.

Accepted when
  • Each injection type has its own control, with adjustable strength.
  • The injection takes effect on the next cycle.
  • Reset returns to a clean state in under two seconds and clears all paths and alerts.
US-22P1UC-21

As a presenter, I want a results card across all scenarios, so that I close with measured numbers rather than claims.

Accepted when
  • It shows attacks caught out of attacks run.
  • It shows average detection time in seconds.
  • It shows false alarms during clean runs — and the target for that number is zero.
EPIC 7

Setup & Self-Calibration

Different vehicles, different sensors
US-23P1UC-22

As an integrator, I want to register a vehicle with the sensors it actually has, so that the engine only runs checks that make sense for it.

Accepted when
  • A vehicle profile lists its available sensors.
  • Only applicable pairs are scored — a truck adds wheels and the road map, a drone adds pressure.
  • Switching profile requires no code change.
US-24P2UniqueUC-22

As the onboard detector, I want to learn each vehicle's own normal behaviour over time, so that thresholds fit that vehicle instead of being guessed by us.

Accepted when
  • Normal drift and noise levels are learned over a number of clean trips.
  • Thresholds are derived per vehicle from that baseline.
  • Sensible defaults apply when no baseline exists yet.
  • Learning never runs while an incident is active, so an attack cannot teach the system to accept itself.
The cut line

What must exist, and in what order

Fifteen stories are marked P0. Build them in this order, because each one makes the next testable:

OrderStoriesWhy here
1US-20, US-21 — scenarios and injectionNothing can be tested until data exists and attacks can be triggered
2US-01, US-02 — health checks and the GPS-free witnessThe witness is the foundation everything else compares against
3US-03 — pair scoringTurns raw data into evidence
4US-11 — the two-path mapThe moment the project becomes demonstrable; do this before adding cleverness
5US-04, US-06 — name the sensor, hold trust steadyThe first unique capability, plus the thing that stops false alarms
6US-05 — attack or faultThe second unique capability and the strongest demo moment
7US-07, US-10 — keep flying, raise the alertCloses the loop from detection to response
8US-14, US-15 — group incidents, draw the zoneThe finale of the demo
9US-17 — evidence recordNeeded for the story, cheap once the rest exists

US-06 is the story teams skip, and it is the one that decides whether this is credible. Without hysteresis the detector fires during ordinary manoeuvres, and every judge asks about exactly that. Build the clean-run scenario early and keep its false-alarm count at zero the whole way through — if that number ever leaves zero, stop and fix it before adding anything new.
